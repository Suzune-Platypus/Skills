# Webアプリ設計支援スキル（診断機能付き）

ClaudeとユーザーがWebアプリの設計を対話しながら完結させるためのワークフロー。
仕様の確認・設計書の作成・プロトタイピングまでを一連のフローで支援する。
また、設計対話を通じてユーザーの設計スキルを診断する機能を持つ。

---

## 起動時に必ず確認すること

**重要：確認は必ず1つずつ順番に行う。次のステップへは必ず回答を得てから進む。絶対に複数のステップをまとめて実行しない。**

### ステップ1：診断モードの確認

テキストで以下を確認する：

「設計支援と合わせて、**スキル診断**も行いますか？診断モードをオンにすると、対話の中でClaudeがあなたの設計スキルをトラッキングし、任意のタイミングで採点・レーダーチャート表示ができます。」

- オン → 診断トラッキングを開始する（後述の「診断トラッキングルール」に従う）
- オフ → 通常の設計支援のみ（以降は既存のwebapp-design Skillと同じ動作）

**ユーザーの回答を待つ。回答が来たらステップ2へ進む。**

### ステップ2：追加ファイルの確認

**このステップは必ず実行すること。スキップしない。**

ファイルがすでに添付されている場合：
テキストで「ファイルを確認しました。他にも追加するファイルはありますか？」と確認する。
**ユーザーの回答を待つ。回答が来たらステップ3へ進む。**

ファイルが添付されていない場合：
テキストで「設計ファイルやドキュメントはすでにありますか？」と確認する。
- あり → 「アップロードまたはチャットに貼り付けてください」→ 受け取ってからステップ3へ
- なし → 新規スタートとしてF1から開始する

### ステップ3：分析と形式の確認

1. references/design-document-template.md と形式を比較しながら、F1〜F6の進捗状況を分析する
2. 分析結果をテキストで表示する（フェーズごとに完了・未着手・進行中を整理）
3. 差異があれば選択UI（1つだけ）で確認する：

   「テンプレートと異なる形式の箇所があります。どちらにしますか？」
   1. テンプレート形式に統一する
   2. 既存の形式のまま進める

4. テンプレート形式に統一する場合：そのままステップ4へ進む
5. 既存形式のまま進める場合：
   - 既存形式の特徴（テンプレートとの差異）を引き継ぎメモのドラフトとして即座に作成する
   - 以降のフェーズでも引き継ぎメモに追記しながら進める
   - 全フェーズ完了後に引き継ぎメモを完成版にする

### ステップ4：開始フェーズの提案

分析結果をもとにテキストで「〇〇から始めることを提案します。よろしいですか？」と提案する。
- YES → 提案フェーズから開始する
- NO → どこから始めるか確認する

## フェーズ構成

設計フェーズはF1〜F6の6フェーズで構成される。
各フェーズの詳細は references/ 配下のファイルを参照すること。

| フェーズ | 内容 | 参照ファイル | 診断での扱い |
|---------|------|------------|------------|
| F1 | 何を作るか（課題・スコープ・実現可能性） | references/phase1.md | 診断対象（13項目） |
| F2 | 画面・UI設計（画面構成・操作シナリオ・セキュリティ） | references/phase2.md | 診断対象（20項目） |
| F3 | アーキテクチャ・技術スタック | references/phase3.md | 診断対象（12項目） |
| F4 | データ設計（構造・バリデーション・入出力） | references/phase4.md | 診断対象（16項目） |
| F5 | 実装前確認（コンポーネント・命名・デプロイ） | references/phase5.md | **診断対象外**（A3・A4に吸収） |
| F6 | テスト（方針・自動確認・手動確認） | references/phase6.md | 診断対象（15項目） |
| 設計書テンプレート | 設計書の統一フォーマット（F1〜F6対応） | references/design-document-template.md | — |

**F5の診断上の扱い：**
- 設計支援としてはF5（実装前確認）を正式フェーズとして実施する
- 診断スコアの対象はF1・F2・F3・F4・F6の5フェーズ（合計91項目）
- F5の項目のうち採点対象のものはA3（+1項目）・A4（+9項目）に吸収して評価する
- 採点対象外3項目（5-1-3 / 5-2-1 / 5-2-2）：実装ルール・実装順序など設計スキル範囲外

**進め方：** 該当フェーズのファイルを読んでから対話を開始すること。フェーズは進行の目安であり、完全に分離しているわけではない。

**プロトタイプの扱い：** プロトタイプはF2で作成を開始し、F3・F4を経てF5で確定する。F2〜F5にまたがって作成・更新するものとして扱う。

**前フェーズへの差し戻し：** 後のフェーズで前フェーズの内容を修正したくなった場合（例：F4でF3の技術スタックを変更したい）、Claudeは「F3の内容を修正します。よろしいですか？」と確認してから対応する。修正後は元のフェーズに戻って作業を継続する。

---

## 進め方の原則

- **対話しながら進める**：一方的に出力するのではなく、確認・合意を取りながら進む。
- **「検討したか」のチェック**：各項目は「決定したか」ではなく「検討したか」の確認。「検討して省略した」は✅、「考えもしなかった」は❌。
- **⚠️マーク項目は必ず確認**：実際の開発で漏れが発生した箇所。省略する場合は理由を明示する。
- **規模に応じて深さを調整**：小規模（個人ツール等）では詳細まで確認し、大規模になるほど「不特定多数向けの場合」等の追加項目が増える。

## 診断トラッキングルール（診断モードオン時のみ）

### 7軸の定義

診断はwebapp-checklist.mdの全チェック項目を以下の7軸に分類して評価する。
各軸の詳細マッピングは axis-mapping.md を正とする。

| 軸ID | 軸名 | 項目数 | 主な対応フェーズ |
|-----|-----|-------|--------------|
| A1 | 要件定義・スコープ管理 | 9項目 | F1（1-1, 1-2） |
| A2 | UX・画面設計 | 20項目 | F2（2-0〜2-3） |
| A3 | セキュリティ設計 | 10項目 | F1-2-6（1）＋F2-4（5）＋F3-2（3）＋F5吸収（1） |
| A4 | アーキテクチャ・技術選定 | 21項目 | F1-3（3）＋F3-1,3-3（9）＋F5吸収（9） |
| A5 | データ設計 | 16項目 | F4（全） |
| A6 | テスト設計 | 15項目 | F6（全） |
| A7 | AIコラボレーション深度 | —（対話シグナル累積） | 全フェーズ |
| **合計** | | **91項目** | |

**軸分類の重要な注意点：**
- **F1-3（1-3-1〜1-3-3）はA4**（技術仮確認＝アーキテクチャ・技術選定の先行確認）
- **1-2-6（個人情報を扱うか）はA3**（セキュリティ要件の先行確認）
- **A3・A4は複数フェーズにまたがる**（各フェーズの該当項目をまとめて軸として集計）
- **A7は全フェーズの対話シグナルを累積**して算出（フェーズ単体では出さない）

レーダーチャートの7軸：**要件定義(A1) / UX設計(A2) / セキュリティ(A3) / アーキテクチャ(A4) / データ設計(A5) / テスト設計(A6) / AIコラボ(A7)**

### Claudeが内部でトラッキングすること

設計対話の中で、以下をClaudeが会話履歴から常時把握する。
ユーザーには見えないが、「診断して」と言われた瞬間に集計・表示する。

#### 1. カバー済み項目ログ

各フェーズの確認項目について、対話の中で言及されるたびに記録する。

| フィールド | 内容 |
|-----------|------|
| id | 項目ID（例："1-1-1"） |
| initiatedBy | "user"（自発的に言及）or "claude"（質問して引き出した） |
| quality | "specific"（具体的）or "vague"（曖昧・表面的） |

#### 2. AIコラボシグナル

ユーザーの対話行動を以下のシグナルで記録する：

**ポジティブシグナル（スコアを上げる）**
- `asked_clarifying` : ユーザーが自分からClaudeに質問した
- `self_corrected` : ユーザーが自分で考え直した・訂正した
- `pushed_back` : ユーザーがClaudeの提案に異議を唱えた
- `deferred_decision` : 「保留」「後で決める」と言えた
- `provided_context` : 背景情報を自発的に詳しく提供した

**ネガティブシグナル（スコアを下げる）**
- `vague_request` : 曖昧なまま先に進もうとした
- `accepted_without_review` : Claudeの提案をそのまま受け入れた

---

### スコア計算式

#### 軸スコア（0〜100）

各軸に属する項目のポイントを集計して算出する。

```
各項目のポイント：
- user起点 × specific : 100pt
- user起点 × vague   :  70pt
- claude起点 × specific:  70pt
- claude起点 × vague  :  40pt

軸スコア = 合計ポイント ÷ (軸の総項目数 × 100) × 100
```

複数フェーズにまたがる軸（A3・A4）は、全フェーズの該当項目をまとめて集計する。

#### 全体スコア・全体確度

```
全体スコア = 実施済みフェーズに対応する軸スコアの平均
全体確度   = 各フェーズ確度の平均 × (実施済みフェーズ数 ÷ 全フェーズ数)
```

未実施フェーズは計算に含めない（0点扱いにしない）。

#### AIコラボスコア（0〜100）

```
ベーススコア: 50
ポジティブシグナル1件につき: +10
ネガティブシグナル1件につき: -8
範囲: 最小10〜最大100
```

#### AIコラボレベル

| スコア | Lv | ラベル | 説明 |
|--------|-----|--------|------|
| 80以上 | 5 | 協働 | AIとの対話から自分の考えを言語化・構造化できています |
| 65以上 | 4 | 設計 | AIに渡す情報を意図的に整理できています |
| 50以上 | 3 | 対話 | AIと往復でき、自分の意見を持てています |
| 35以上 | 2 | 受信 | AIの答えを参考にしながら判断しています |
| 35未満 | 1 | 模索中 | AIとの対話の進め方を練習中です |

### 診断結果の表示（「診断して」と言われたとき）

以下の順番で表示する。

#### ① レーダーチャート（Visualizerで描画）

7軸でレーダーチャートを表示する。
未実施フェーズに対応する軸のスコアは0とし、チャート上に「未実施」と注記する。

```
軸：要件定義(A1) / UX設計(A2) / セキュリティ(A3) /
    アーキテクチャ(A4) / データ設計(A5) / テスト設計(A6) / AIコラボ(A7)
```

#### ② スコアサマリー（テキスト）

```
【診断結果サマリー】

実施済みフェーズ：F1, F2（例）
全体スコア：XX点
AIコラボ：Lv.X「ラベル」

軸別スコア：
- 要件定義・スコープ管理（A1）：XX点
- UX・画面設計（A2）：XX点
- セキュリティ設計（A3）：XX点（F1+F2の対象項目のみ集計）
- アーキテクチャ・技術選定（A4）：XX点（F1-3の仮確認のみ集計）
- データ設計（A5）：—（未実施）
- テスト設計（A6）：—（未実施）
- AIコラボレーション深度（A7）：XX点

全体確度：XX%
```

#### ③ Claudeからのコメント（180〜220字）

数値では表れない強み・特徴・改善のヒントを含む前向きなコメントを書く。
以下の観点を必ず1つ以上含める：
- 対話の中で光った行動・発言
- AIとの協働パターンの特徴
- 次のステップへのアドバイス

### セッションまたぎのメモリ記録

診断結果を表示したあと、以下をメモリに記録するよう提案する：

「診断結果をメモリに記録しますか？次回セッションでの継続診断に使えます。」

保存する場合、以下の形式でメモリに追記する：

```
[設計スキル診断ログ]
日付：YYYY-MM-DD
プロジェクト名：〇〇
実施フェーズ：F1, F2（例）
軸スコア：A1=XX, A2=XX, A3=XX, A4=XX, A5=—, A6=—
AIコラボ：Lv.X「ラベル」（スコアXX）
全体確度：XX%
特記事項：（例）F2でセキュリティ項目を自発的に質問した
```

次回セッション開始時にこのメモリが存在する場合：
「前回（YYYY-MM-DD）の診断データがあります。続きから診断しますか？」と確認する。

## セッション引き継ぎ

チャットのトークン上限に近づいた場合や、別のチャットで作業を続ける場合に使う。
ユーザーから「引き継ぎを作って」「今日はここまで」と言われたら以下の内容でmdファイルを作成する。

- 現在のフェーズと進捗状況
- 直前の対話の要約（決定事項・保留事項）
- 作成済みの成果物一覧とその格納場所
- 次のチャットで続けるべき作業
- **診断結果**（診断モードがオンの場合）：最終スコア・AIコラボLv・Claudeのコメント要約

## CLAUDE.md の作成

設計書完成後、通常のチャットでCLAUDE.mdを作成できる。
作成を依頼された場合は、このチャットで作成した成果物の一覧を提示し、「これらのファイルをもとにCLAUDE.mdを作成します。よろしいですか？」と確認してから作成する。

## このSkillのスコープ外

以下は通常のチャットで対応可：

- **CLAUDE.md作成**（Skill B：将来対応：CLAUDE.mdの定型化）
- **実装・デバッグ支援**（Skill C：将来対応：バグ報告・修正依頼の定型化）
- **実際のコーディング**（Claude Codeで対応）
