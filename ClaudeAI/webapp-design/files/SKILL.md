# Webアプリ設計支援スキル

ClaudeとユーザーがWebアプリの設計を対話しながら完結させるためのワークフロー。
仕様の確認・設計書の作成・プロトタイピングまでを一連のフローで支援する。

---

## 起動時に必ず確認すること

**重要：確認は必ず1つずつ順番に行う。次のステップへは必ず回答を得てから進む。絶対に複数のステップをまとめて実行しない。**

### ステップ1：追加ファイルの確認

**このステップは必ず実行すること。スキップしない。**

ファイルがすでに添付されている場合：
テキストで「ファイルを確認しました。他にも追加するファイルはありますか？」と確認する。
**ユーザーの回答を待つ。回答が来たらステップ2へ進む。**

ファイルが添付されていない場合：
テキストで「設計ファイルやドキュメントはすでにありますか？」と確認する。
- あり → 「アップロードまたはチャットに貼り付けてください」→ 受け取ってからステップ2へ
- なし → 新規スタートとしてF1から開始する

### ステップ2：分析と形式の確認

1. references/design-document-template.md と形式を比較しながら、F1〜F6の進捗状況を分析する
2. 分析結果をテキストで表示する（フェーズごとに完了・未着手・進行中を整理）
3. 差異があれば選択UI（1つだけ）で確認する：

   「テンプレートと異なる形式の箇所があります。どちらにしますか？」
   1. テンプレート形式に統一する
   2. 既存の形式のまま進める

4. テンプレート形式に統一する場合：そのままステップ3へ進む
5. 既存形式のまま進める場合：
   - 既存形式の特徴（テンプレートとの差異）を引き継ぎメモのドラフトとして即座に作成する
   - 以降のフェーズでも引き継ぎメモに追記しながら進める
   - 全フェーズ完了後に引き継ぎメモを完成版にする

### ステップ3：開始フェーズの提案

分析結果をもとにテキストで「〇〇から始めることを提案します。よろしいですか？」と提案する。
- YES → 提案フェーズから開始する
- NO → どこから始めるか確認する

## 成果物の出力形式

**デフォルトはmdファイル。** ユーザーが「docxで作って」と言ったタイミングで `docx` Skillを参照してdocx形式に切り替える。それ以外は確認不要。

| 成果物 | デフォルト形式 |
|--------|--------|
| 設計書（要件定義・画面設計等） | md（docx希望時はdocx Skillを参照） |
| 画面フロー・ER図 | mermaid |
| プロトタイプ | React |
| データ構造定義 | md |
| テストケース | md |

---

## フェーズ構成

設計フェーズはF1〜F6の6フェーズで構成される。
各フェーズの詳細は references/ 配下のファイルを参照すること。

| フェーズ | 内容 | 参照ファイル |
|---------|------|------------|
| F1 | 何を作るか（課題・スコープ・実現可能性） | references/phase1.md |
| F2 | 画面・UI設計（画面構成・操作シナリオ・セキュリティ） | references/phase2.md |
| F3 | アーキテクチャ・技術スタック | references/phase3.md |
| F4 | データ設計（構造・バリデーション・入出力） | references/phase4.md |
| F5 | 実装前確認（コンポーネント・命名・デプロイ） | references/phase5.md |
| F6 | テスト（方針・自動確認・手動確認） | references/phase6.md |
| 設計書テンプレート | 設計書の統一フォーマット（F1〜F6対応） | references/design-document-template.md |

**進め方：** 各フェーズを開始する前に、必ず該当フェーズの `references/phase*.md` を読むこと。特に「このフェーズのアウトプット」セクションを確認してから対話を始める。フェーズは進行の目安であり、完全に分離しているわけではない。

**プロトタイプの扱い：** プロトタイプはF2で作成を開始し、F3・F4を経てF5で確定する。F2〜F5にまたがって作成・更新するものとして扱う。

**前フェーズへの差し戻し：** 後のフェーズで前フェーズの内容を修正したくなった場合（例：F4でF3の技術スタックを変更したい）、Claudeは「F3の内容を修正します。よろしいですか？」と確認してから対応する。修正後は元のフェーズに戻って作業を継続する。

---

## 進め方の原則

- **対話しながら進める**：一方的に出力するのではなく、確認・合意を取りながら進む。
- **「検討したか」のチェック**：各項目は「決定したか」ではなく「検討したか」の確認。「検討して省略した」は✅、「考えもしなかった」は❌。
- **⚠️マーク項目は必ず確認**：実際の開発で漏れが発生した箇所。省略する場合は理由を明示する。
- **規模に応じて深さを調整**：小規模（個人ツール等）では詳細まで確認し、大規模になるほど「不特定多数向けの場合」等の追加項目が増える。

---

## アウトプット作成のルール

対話が完了しても、アウトプットを作成するまでフェーズは完了していない。
以下の4つのタイミングで未作成のアウトプットを確認する。このステップをスキップしてはならない。

| タイミング | 動作 |
|-----------|------|
| 内容確認直後 | 合意した内容をもとに「〇〇を作成しましょうか？」と自然に促す |
| フェーズ終了時 | 未作成のアウトプットがあれば一覧を提示して確認する |
| 次フェーズ開始時 | 前フェーズの未作成分があれば確認してから次フェーズに進む |
| F6終了時 | 全フェーズを通じた未作成分があれば最後にまとめて確認する |

作成しない場合は、作業ログに「未作成（理由：〇〇）」として記録する。

## セッション引き継ぎ

チャットのトークン上限に近づいた場合や、別のチャットで作業を続ける場合に使う。
ユーザーから「引き継ぎを作って」「今日はここまで」と言われたら以下の内容でmdファイルを作成する。

- 現在のフェーズと進捗状況
- 直前の対話の要約（決定事項・保留事項）
- 作成済みの成果物一覧とその格納場所
- 次のチャットで続けるべき作業

---

## CLAUDE.md の作成

設計書完成後、通常のチャットでCLAUDE.mdを作成できる。
作成を依頼された場合は、このチャットで作成した成果物の一覧を提示し、「これらのファイルをもとにCLAUDE.mdを作成します。よろしいですか？」と確認してから作成する。

---

## このSkillのスコープ外

以下は通常のチャットで対応可：

- **CLAUDE.md作成**（Skill B：将来対応：CLAUDE.mdの定型化）
- **実装・デバッグ支援**（Skill C：将来対応：バグ報告・修正依頼の定型化）
- **実際のコーディング**（Claude Codeで対応）
